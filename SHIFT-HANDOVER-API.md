# Shift handover (SCHEDULE-004)

The native `/api/lanyard/command` door accepts `shiftwork.save` from the owner or a manager of the shift's cafe. Supply `shiftId`, `shiftRevision`, `notes` (up to 4000 characters), and `tasks` (up to 30 strings of 280 characters). When editing, supply the current instruction `revision` as well. Read `shiftwork` in `/api/lanyard/state` for the saved revision and generated task ids. Edits keep previous instruction versions for managers and create new task ids; prior confirmations never complete edited wording.

The current assignee can send `shiftwork.respond` with `shiftId`, `shiftRevision`, instruction `revision`, `completed` (current task ids), and an optional `blocker` (up to 2000 characters). Responses are immutable handover entries in `taskanswers`, each carrying its author, timestamp, exact instruction revision and completed task wording. Send a later entry to update the handover; earlier entries remain. Managers inspect these entries through the same state door. An offered shift does not grant instructions before assignment. Reassignment or supersession removes the previous assignee's instruction access; their prior responses remain readable by them and the authorized cafe managers. Canceled shifts accept no new responses.

In Schedule, a cafe manager opens **Shift handover → Edit handover**, adds notes and one task per line, and chooses each work area's job and end minute from shift start. The ordered areas must cover the full shift. Save rechecks the employee's qualifications; a reassignment also rechecks each area. The current assignee opens the same card on their phone, checks completed tasks and sends a blocker with an optional file (up to 1 MB). The manager sees the retained responses and can download the file. Printed and wall schedules include none of this operational content.

`shiftwork.save` also accepts `segments: [{until, job, area}]`, at most 20, with increasing end minutes covering the shift. An instruction save with areas changes the enclosing shift revision, so reload state before responding. `shiftwork.respond` accepts `attachment: {name, type, data}` with base64 file data; response file downloads use `/api/lanyard/handover/<answer-id>/files/<file-id>` and the same current native access checks as the response.

Time submission pins the area's instruction revision. Approval reconciles actual payable minutes to areas, extending the first/last for early/late work and proportionally allocating unpaid or rounded minutes with whole-minute largest-remainder allocation. Time shows each area's hours and retained job-rate cost beside the enclosing total. Labor reports and payroll count the areas once; payroll files add job, work-area, location and enclosing source-time columns for split lines, and a correction exports per-area signed differences with one claim for the enclosing timesheet. Editing instructions later never changes submitted work's pinned plan. Clear areas before changing a shift's duration, then enter a plan for its new duration.
